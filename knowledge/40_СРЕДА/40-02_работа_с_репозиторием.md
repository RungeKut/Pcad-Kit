# Работа с репозиторием

Набор живёт в `https://github.com/RungeKut/Pcad-Kit` и разворачивается
на нескольких машинах.

## Обязательный порядок

```bash
cd "$PKIT_HOME"
git pull --rebase                                      # В НАЧАЛЕ работы
# ... правки набора ...
git diff                                               # прочитать глазами
git add -A && git commit -m "что и почему" && git push # СРАЗУ после правки
```

Отправлять после каждой смысловой правки, а не в конце сессии: новая
запись в `knowledge/`, изменение `pkit/`, правка `SKILL.md`. Знание,
оставшееся на одной машине, для остальных не существует.

Push отклонён — значит кто-то опередил: `git pull --rebase`, затем push
снова. **После слияния — перечитать слитое**: git сливает текст, а не
смысл. Соседние наборы уже получали так испорченную таблицу индекса и
раздел, спорящий сам с собой.

В отличие от соседних наборов, здесь **нет** `check_docs.py`,
`stoplist.txt` и хука `commit-msg`: механической проверки нет, поэтому
`git diff` глазами перед коммитом — единственный заслон.

## Подготовка коммита: изделие в набор не попадает

Репозиторий **публичный**. Правило — п. 8 `00_ПРАВИЛА.md`: ни названий,
ни децимальных номеров, ни имён цепей и компонентов изделия, ни путей
проектов — ни в файлах, ни в тексте коммита. Примеры — на отвлечённой
схеме. Описание узла, по которому изделие узнаётся без названия, не
ловит никто — за этим `git diff` глазами.

## GitHub без gh

На машине может не быть `gh`. Хватает git с сохранённым доступом к
github.com (Диспетчер учётных данных Windows) и REST API:

```bash
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p')
curl -s -H "Authorization: token $TOKEN" https://api.github.com/user/repos \
     --data-binary @payload.json     # JSON из файла, не из командной строки
```

Две проверенные тонкости (пойманы при первичной публикации этого
набора, 2026-10-08):

* JSON с кириллицей из командной строки curl под Git Bash ломается
  (`400 Problems parsing JSON`) — тело запроса писать в файл
  (`--data-binary @file`);
* прокси в `http.<url>.proxy` (корпоративный, с MITM-подменой
  сертификата) даёт `SSL certificate problem` / `511`; если прямой
  доступ есть — настройку прокси для github.com убрать
  (`git config --global --unset http.https://github.com.proxy`).

**`gh auth login` из агентской оболочки не запускать** — интерактивная
команда без терминала висит вечно. Нет доступа — попросить человека
выполнить вход в своём терминале.

## Вклад без права записи: pull request

Push в репозиторий отклонён с `403` / `Permission denied` — право записи
только у владельца. Доступ не подбирать и не обходить: изменение уходит
**pull request'ом из своего форка**:

```bash
gh repo fork RungeKut/Pcad-Kit --remote --remote-name=fork
git switch -c <тема-латиницей>
# ... правки набора; перед пушем — тот же порядок, что перед коммитом:
# git diff глазами, чистый текст коммита ...
git push fork <тема-латиницей>
gh pr create --repo RungeKut/Pcad-Kit --title "что и почему" \
     --body "<суть изменения>"
```

Правила те же, что для коммита: обезличивание (заголовок и текст PR —
тоже), записи базы по `00_ПРАВИЛА.md` (шапка с `verified`, строка в
`INDEX.md`, строка в `CHANGELOG.md`). Один PR — одна тема. Свой PR не
сливать: решает владелец.

Нет `gh` — то же через REST API по токену из `git credential fill`
(раздел «GitHub без gh»): форк — `POST /repos/{owner}/{repo}/forks`,
далее push в свой форк обычным git, PR —
`POST /repos/{owner}/{repo}/pulls` с `head` = `<логин>:<ветка>`. По
документации GitHub API; на машинах набора этот путь не проверен.

## Владельцу: разбор pull request'ов

Чужие правки приходят PR'ами и ждут разбора: в начале работы, вместе с
обязательным `git pull --rebase`, — проверить и принять или вернуть:

```bash
gh pr list                             # пусто — работаем дальше
gh pr diff <N>                         # прочитать целиком, глазами
gh pr checkout <N>                     # и осмотреть в рабочей копии
gh pr merge <N> --rebase               # история линейная
git pull --rebase                      # подтянуть слитое в клон
```

Принимается только то, что прошло бы обычный коммит: обезличивание (diff
читается глазами), записи базы по правилам. **Особое внимание —
исполняемым файлам** (`tools/setup.ps1`, `tools/dbx-host/DbxHost.cs`,
`*.py`): после слияния они окажутся на машине владельца и будут
запускаться. Не прошло проверку — не сливать, а вернуть с пояснением:
`gh pr review <N> --request-changes --body "что поправить"`. «Слить и
поправить потом» нельзя: репозиторий публичный, увидеть содержимое может
кто угодно сразу после слияния.

Нет `gh` — список и слияние через REST API:
`GET /repos/{owner}/{repo}/pulls?state=open`, слияние —
`PUT /repos/{owner}/{repo}/pulls/{N}/merge` с `{"merge_method":"rebase"}`.
Слияние, отвечающее 403, — вы не владелец: разбор пропустить.

## Установка на новой машине

```powershell
git clone https://github.com/RungeKut/Pcad-Kit.git
cd Pcad-Kit
powershell -ExecutionPolicy Bypass -File tools\setup.ps1
```

Затем перезапустить Kimi Code: скиллы перечисляются при старте.
